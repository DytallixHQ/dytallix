# Mainnet launch simulations

Status: planned; no run has passed. Seven full launch simulations (R01 to R07) must pass on the final candidate before genesis (T06). Component checks do not qualify a launch. The decisions are in the [simulation plan approval](../../../launch/approvals/P01_T06_SIMULATION_PLAN_2026-10-11.json); the requirements are the launch brief's, kept verbatim in [launch-rehearsals.json](launch-rehearsals.json) (`full_launch_runs`), and the run definitions in the [execution plan](../../../launch/MAINNET_EXECUTION_PLAN.md#seven-simulation-runs).

## Where and when

- **Where.** The two production hosts (the validator, and the sentry, which also serves clients; [two seats](../../../launch/approvals/P01_E05_TWO_SEATS_2026-10-11.json)), before genesis, under the solo launch profile. Every tool is first built and proven in the CI staging network ([host install workflow](../../../.github/workflows/host-install.yml)).
- **When.** Task-driven: after Hashlock's audit fixes, on the final candidate, one run after another ([audit approval](../../../launch/approvals/P01_E06_AUDIT_2026-10-10.json), [order of work](../../../launch/GENESIS_FRAMEWORK.md#6-order-of-work)). The staging runs before the freeze (E03, the T suites, the capacity measurements, the kit drills) come first and find defects early.
- **Length.** Each run operates for 24 hours after its genesis; R07 spans T−6h to T+24h. No checkpoint is compressed.
- **Before the runs.** During staging, a [statistical campaign](#statistical-campaign-staging) of about 15 to 21 days of host time measures attacks, faults, performance and endurance with confidence.

## Every run

1. **Clean hosts.** Each host is rebuilt from the provider's Ubuntu 24.04 image and installed from its sealed rehearsal bundle (`install.sh`).
2. **Rehearsal identity.** A fresh rehearsal chain ID per run (never one naming mainnet), fresh throwaway node keys, and a rehearsal root authority, three of five, from throwaway kits; never production keys.
3. **Spendable rehearsal genesis.** The production allocation (buckets, treasury, holder grants, validator self-bond, DRT bootstrap) mapped deterministically to rehearsal accounts whose keys the harness holds, plus wallet accounts for the load. The mapping is recorded.
4. **Values.** Every production value, except R01 to R06's recorded timing set (below).
5. **Services.** The real alerting and uptime services, the backup bucket, the staging agent on each host, and, for R03 and R06, the load machines.
6. **Evidence.** Recorded as in [Evidence](#evidence) and hashed.

### Shortened timings (R01 to R06 only)

So that each lifecycle completes inside a 24-hour run, these production values are shortened and listed, with their production values, in every run record ([approval](../../../launch/approvals/P01_T06_REHEARSAL_TIMINGS_2026-10-12.json), P01, 12 October 2026). The set is the `rehearsal` profile in [TIMINGS.json](../../../launch/simulations/TIMINGS.json); `staging_chain.py --timings rehearsal` builds a chain with it, and the CI install job does so on every change.

| Value | Production | Rehearsal |
|---|---|---|
| Upgrade and handover notice (also the kit replacement notice) | 120,960 blocks | 720 blocks (1 hour) |
| Governance deposit and voting periods | 120,960 blocks each | 720 blocks each |
| Governance timelock | 34,560 blocks | 360 blocks |
| Evidence age and margin (unbond maturity) | 241,920 + 720 blocks; 14 days + 1 hour | 2,880 + 120 blocks; 4 hours + 10 minutes |
| Snapshot interval | 17,280 blocks | 720 blocks |
| State sync trust period | 168 hours | 1 hour |

The tools derive and check the rest before building: the trust period stays below the evidence age; a restore trusts a copy for the evidence age less a fourteenth (about 3 hours 43 minutes), longer than the newest backup copy can be (a snapshot interval plus the hourly backup and its 15-minute delay, about 2 hours 15 minutes); block and second ages agree at 5-second blocks; and unbonding (about 4 hours 10 minutes), a full governance cycle (2 hours 30 minutes) and the notice fit in the run. A restore's trust counts from the copy's header, so in R01 to R06 a lost host must be restored within about 88 minutes of the loss in the worst case (production: about 12 days); R02's restore runs inside that, and its 4-hour rebuild target is checked at production timings (the CI restore drill and the campaign's heavy faults).

R07 uses the exact production values.

### The staging agent

The production hosts are console-only. While they serve as staging, each runs a small agent:

- It polls the backup bucket over the host's `curl`, outbound only, for command files.
- It runs a command only if the founder's ML-DSA-65 staging command key signed it and the command is on a fixed allowlist: the run steps below, such as start, stop, fault injection and status capture. Key custody, encryption, store layout and the allowlist are approved ([staging agent approval](../../../launch/approvals/P01_T06_STAGING_AGENT_2026-10-14.json)).
- It uploads each result encrypted, like the metric history. TLS stays transport only.
- It is never part of a release, and the wipe before the production install removes it.
- Its install on both hosts for the rehearsal chain `dytallix-staging-2`, and the quick-fault runs there (up to 30 rounds of the sentry's quick faults and 30 validator restarts), are approved ([approval](../../../launch/approvals/P01_T06_AGENT_INSTALL_2026-11-02.json)); heavy faults and the other campaign parts on the real hosts need their own.

The design, its threat model and the choices still open for P01 are in [staging agent v1](../architecture/staging-agent-v1.md).

### The load machines

Four to eight small rented machines, each with its own address: Hetzner Cloud's smallest x86 servers in the hosts' own project, in nbg1, fsn1 and sin (never hel1, the sentry's location), rented by the hour for R03, R06 and the campaign's flood runs only and deleted after each use ([approval](../../../launch/approvals/P01_T06_LOAD_MACHINES_HETZNER_2026-11-03.json), replacing DigitalOcean in the [reconcile approval](../../../launch/approvals/P01_T06_AGENT_RECONCILE_2026-10-20.json) and dropping the rule that they run outside the hosts' provider; the account-wide suspension risk is accepted there). They reach the chain only through the sentry's public client channel, within its production limits (16 connections, 2 per address), and hold only rehearsal keys. **Renting them is built** (`load_machines.py`): `up` creates them (each labelled with its run, a throwaway SSH key per run, spread across the locations) and starts a watchdog that deletes them at the run's deadline; `down` deletes a run's machines at once and `reap` every labelled machine. The limits are in code: at most 8, only the smallest types, at most 12 hours, never two runs at once, and a failed `up` deletes what it made. Because the hosts share the project, every other server keeps Hetzner's delete protection (`up` refuses otherwise) and the tool deletes only servers it labelled and named. It runs the hcloud CLI with the project's named context, so no token passes through it. **Driving the load from them is built** (`load_workers.py drive`): the founder's machine keeps the funder, funds the fleet and splits it into one disjoint share per machine; each machine gets only its share's throwaway keys, the release CLI, the load tools and the chain pin, primes its wallets, and from one start time sends its part of the rate over its own two connections. The run is judged once, on every machine's rows (load.py's evidence, so `load.py verify` checks it), and its workers' connections must fit the channel (at most 8 machines of 2, and fewer while the founder's machine is on the channel). CI proves it with three workers in their own network namespaces and addresses on the staging bridge.

## Pass criteria

Approved thresholds (D14-Q02):

| Area | Criterion |
|---|---|
| **Integrity** (every run; a failure stops the run) | Zero conflicting finalized blocks. The same app hash on every node at every checkpoint. Supply reconciles exactly: DRT genesis plus emitted minus burned, DGT unchanged, and the account totals equal the supply counters. No committed block lost in any recovery. |
| **Liveness** (outside injected faults) | Median block interval at most 6 s; 99th percentile at most 10 s. |
| **Inclusion** | At half capacity, 99% of valid transactions committed within 2 blocks. At full capacity, no valid transaction lost: each is committed or refused at admission. |
| **Recovery** | Blocks again within 5 minutes of a validator process restart; the sentry caught up within 2 minutes of a network heal; a destroyed sentry rebuilt within 4 hours; a lost validator host within 8 hours. Every injected fault raises its alert and resolves after recovery. |
| **Load** (R06) | Full capacity, about 180 basic Sends a block, for 1 hour; half capacity for 6 hours; across 1,000 wallets. |

A missed threshold fails the run. A failure is fixed in a new candidate, with a documented diff, and the affected runs are rerun on it; all seven must pass on the final candidate.

## One validator

The launch has one validator, so some of the brief's network scenarios mean something specific:

- **Stopping the validator halts the chain.** Every host raises a halt alert. A restart resumes it with no procedure, since the double-sign startup check is 0 while there is one validator. The unit does not restart itself, so a crashed validator needs the console (or the agent, in staging).
- **A validator partition does not halt it.** Holding all the power, the validator keeps committing alone. The sentry stalls, and the status page answers 503 after 60 seconds. On reconnect it redials within 60 seconds and catches up.
- **Latency and packet loss** change propagation and how fresh the sentry's view for clients is, not consensus.
- **A second copy of the validator key** is the catastrophic case. A duplicate vote removes the validator for good and ends the chain, and an isolated copy would finalize its own fork. Nothing automatic stops it: today only the fence-first rule ([validator recovery](../operations/validator-recovery.md)) and the pinned peer addresses stand in the way. R05 checks that a second copy at another address cannot reach the network, and the residual risk is recorded.

## Statistical campaign (staging)

The seven runs are pass/fail qualification. Before them, during staging and before the freeze, the production hosts run a longer campaign that measures behavior with statistical confidence ([simulation plan approval](../../../launch/approvals/P01_T06_SIMULATION_PLAN_2026-10-11.json)). It uses rehearsal identities, the tools below, and its results go to Hashlock with the frozen candidate.

| Part | Rule | Host time |
|---|---|---|
| **Attacks on core functions** | Each attack type is attempted at least 3,000 times with zero successes. By the rule of three, that bounds its success rate below 1 in 1,000 at 95% confidence. Connection- and network-level attacks are repeated about 30 times each. | About 2 to 4 days in all |
| **Faults and recovery** | Each quick fault (process kill, peer drop, partition, latency, sentry restart) about 30 times; each heavy fault (host rebuild, snapshot restore, validator recovery) 3 to 5 times; recovery times recorded as distributions | About 3 to 5 days in all |
| **Performance** | Block intervals, inclusion delay and response times: a day gives about 17,280 blocks, enough for the median, p95 and p99; p99.9 comes from the whole endurance run | Within the endurance run |
| **Endurance** | At least 15 days continuous at the exact production values, with background load and periodic half-capacity periods: full unbonding (14 days), governance deposit and voting (7 + 7 days), a release handover after its 7-day notice, at least 15 epochs and snapshots, and state and memory growth | At least 15 days; the attack and fault campaigns interleave inside it |

The attack types cover every core function:

- **Transactions:** invalid, wrong-key and truncated ML-DSA-65 signatures; malformed, non-canonical and oversized envelopes; the wrong chain or network; expired transactions; stale, future and conflicting nonces; duplicate bytes and re-signed copies of a pending intent; fee caps below the minimum; spending more than the eligible balance; too many actions.
- **Staking:** a validator's self-bond below the minimum; bonds to an unknown validator; unbonding more than is bonded; early withdrawal; repeated reward claims; validator registration with a bad possession proof or a reused key. A delegation bond has no minimum by design ([types](../../../launch/approvals/P01_T04_ATTACK_TYPES_2026-11-04.json)).
- **Governance:** proposals below the deposit; votes without a bond, repeated or after the period; parameter changes outside the genesis bounds. No transaction can start or repeat a governance execution, so replayed execution is not a type ([types](../../../launch/approvals/P01_T04_ATTACK_TYPES_2026-11-04.json)).
- **Root controls:** too few signatures; keys from the wrong epoch; a replayed sequence; an expired window; non-canonical encoding; a kit replacement while frozen.
- **Recovery:** replayed and wrong-key recovery transactions.
- **Endpoint and RPC:** oversized bodies, header and connection floods beyond the limits, slow clients, invalid handshakes, a wrong pin, methods outside the allowlist.
- **Network:** latency, packet loss, partitions and peer instability; wrong-key and malformed peers come from the E03 runner.

Any successful attack is a defect, fixed before the freeze. Simulation cannot cover events rarer than about once a day with confidence; the audit and the public review cover those. Each attack listed above is one type: at least 3,000 attempts per type for transactions, staking, governance, root controls and recovery, and about 30 per endpoint, RPC and network type, each with zero successes ([simulation inputs approval](../../../launch/approvals/P01_T06_SIMULATION_INPUTS_2026-10-14.json)).

**The transaction family's driver is built** (`attacks.py`): each type attempted with its own bytes through the client channel, counted only when the node refuses it for the type's reason; an admitted attempt is a success, a refusal for another reason fails the type, and a positive control after each type must commit. All seventeen types are built. The release CLI checks a fee cap below the minimum and too many actions before it signs, so for those two the attack client (`node/tools/attack-client`, built for the campaign and CI only, never part of a release) re-signs a transaction the CLI made with the account's own key after the one change: a cap below the gas limit times the gas price, or one action more than the profile allows (canonical bytes, the count the only fault). It checks its signature and that the profile refuses the forgery for that reason, and each row keeps those checks, since the node's word for too many actions is its decoder's "Malformed ordinary envelope". The results collector publishes the family's attempts and successes. CI runs each built type 10 times; the staging hosts run 3,000. The network family follows; an attack the node refuses only when the block runs (most staking and governance types) counts as refused when it fails for the type's own reason and a state read shows nothing changed but the fee ([decisions](../../../launch/approvals/P01_T04_ATTACK_DECISIONS_2026-11-04.json)). A repeated reward claim and a proposal below the deposit commit by design, so each counts as refused when the reads show it did nothing: the claim paid nothing, the proposal never reached a vote ([types](../../../launch/approvals/P01_T04_ATTACK_TYPES_2026-11-04.json)).

**The endpoint and RPC family's driver is built** (`endpoints.py`): from addresses of their own, connection floods over the client channel's per-address and total bounds and over the status page's, stalled connections, invalid handshakes (a bad magic, version, type or length, another network, another endpoint's key, an encapsulation key that fails the FIPS 203 check, a forged finish after the endpoint's real offer) and header floods, each closed or refused by the listener. A listener that serves one is a success, and after each type a positive control from another address must read the height through the channel and the status page, rising. The status page now takes at most 2 connections from one address, as the channel does, so one address cannot keep the uptime checker out ([decisions](../../../launch/approvals/P01_T04_ATTACK_DECISIONS_2026-11-04.json)). Six of the nine types are built: an oversized body, a method outside the allowlist and a wrong pin need an attack client that completes the handshake (built for the campaign and CI only, never shipped), and until then the family's attempts stay below the target. CI runs each built type 30 times from nine network namespaces on the staging bridge; on the real hosts the types that need several addresses run from the load machines.

**The root-control family is built** (`root_controls.py`, the CI `root-control-campaign` step after the kit replacement drill): all six types, each from a genuine control the release tools and the staging kits make. Too few signatures leaves one out of a fresh freeze. Keys from the wrong epoch swaps one for a signature by the freeze key the kit drill replaced, made from a stale key list as an old kit would. Non-canonical encoding sends the freeze's own value and signatures in other bytes (a space, an escaped letter, two fields swapped). An expired window is a freeze signed for 24 blocks and sent after them. A replayed sequence is the kit drill's committed freeze and resume, byte for byte, checked at admission (the engine's cache answers a broadcast of committed bytes first). A kit replacement while frozen is a fresh replacement the node admits until the fresh freeze holds the chain, refused while it does, and never sent unfrozen; the chain is resumed whatever froze it. The first attempt of each type is the genuine control with its one fault; later attempts change one more field by the attempt number (the incident digest, a replacement's last height), so each has its own bytes and its signatures no longer verify, which is sound because every check these types name runs before the node verifies a signature. Each row records which fields differ from the genuine control and whether its bytes are canonical, and counts as refused only when the node gave the type's reason and those differences are exactly the type's. After each type a control the node should admit is checked (the fresh freeze; while frozen, the resume; after it, the replacement) and the chain's height must rise. CI runs each type 10 times; the staging hosts run 3,000.

**The staking family is built** (`staking.py`, the CI `staking-campaign` step after the transaction family): all seven types, every attempt signed by the release CLI and its possession proofs by the release's validator key tool. The staging genesis approves a campaign operator for a validator ID it does not register ([campaign operator](../../../launch/approvals/P01_T04_CAMPAIGN_OPERATOR_2026-11-05.json)), and the registrations come from it: a fresh key with its self-bond below the minimum; a registered validator's key (in CI the runner's own validator key, read in place) with a full self-bond; and the fresh key with one byte of its proof changed. The node refuses the bad proof at admission. The other types pass admission and fail when the block runs, charged their fee: a bond to an unknown validator, unbonding more than is bonded, withdrawing an unbonding entry long before it matures, and a reward claim by a wallet whose whole bond was unbonded and whose rewards were claimed, watched to accrue nothing. Each goes one attempt a wallet a round, followed to its receipt with its wallet's account read before and after, and counts as refused only when the receipt names the type's rule and nothing changed but the fee the receipt charged and the one nonce it spent: liquid DGT, bonds, pending bond and unbonding, and for the registrations and bonds the validator set; a repeated claim counts when it paid nothing. Each row keeps its attempt's fault as read from the chain (the key against the validator set, the proof, the amount against the minimum or the bond, the target, the entry's age) and counts only when the fault is the type's. The positive controls: a valid registration checked at admission before and after (never sent), the claimer's first claim paying, and a valid bond and unbond committing. CI runs each type 10 times; the staging hosts run 3,000, the two block-run registrations sharing the one operator's block slot.

**The governance family is built** (`governance.py`, the CI `governance-campaign` step after the staking family): all five types, every attempt a governance transaction the release CLI signs and sends in one step. A governance transaction has no receipt, so each result is read from the block that holds it (`block` and `block_results`, found by the engine hash the CLI reports): code 3 and the rule for a failure the block charged. A proposal below the deposit is a bonded proposer's no-op proposal (the active set size the chain has) with no deposit, or with a deposit of 1 + k udgt; the node refuses a zero deposit at admission, so none is sent. It commits by design and counts as refused when its proposal and deposit committed and the reads show it collecting exactly that deposit, below the minimum, with nothing changed in the proposer's account but the two fees, the deposit and any refunds due. Proposals take the chain's next ID, so these go one at a time on the whole chain. An out-of-bounds change is a bonded voter's proposal of the active set size or the minimum self-bond just above or below the genesis bounds, at the next ID; it fails before the ID is checked, so several go in a round. The votes need a vote open: a proposal with the minimum deposit reaches its vote at its deposit close. A vote without a bond comes from a wallet never bonded (no weight in the vote's snapshot), a repeated vote from a bonded voter whose first vote counted, and a late vote from a bonded voter that never voted, signed after the vote's end. A proposal is kept one block after its vote ends and then removed, so a late vote counts as refused for VOTING_CLOSED or PROPOSAL_UNKNOWN when its row proves it late ([late votes](../../../launch/approvals/P01_T04_LATE_VOTES_2026-11-05.json)). Each attempt's wallet is read before and after, and each counts only when the block names its rule and nothing changed but the fee (the larger of the gas used and the minimum gas, at the gas price) and the one nonce: liquid DGT, bonds, pending bond and unbonding; the voter's vote; no proposal stored for the wallet. Each row keeps its fault as read from the chain (the deposit against the minimum, the value against the bounds, the proposer's bond, the ID against the next one, the voter's snapshot weight and earlier vote, the height against the vote's end). Where a deposit period ends within the run, every proposal the campaign made is read again as its close passes (finished below the minimum, or removed while a vote opened then would still run), the proposer's liquid DGT must rise by each deposit at its close, and every vote round's tally may change only when a vote was admitted. The positive controls: an in-bounds proposal commits before and after; where votes run, the vote's proposal reaches its vote and each repeated voter's first vote counts. CI keeps the production governance periods, where no vote opens, and runs the first two types 10 times each. On the staging hosts, under the rehearsal timings (720-block periods), all five run 3,000 times: the proposals below the deposit alone take about 6 to 12 hours at 5-second blocks, one proposal in flight at a time, and the votes in the period need enough wallets to fit their attempts in its 720 blocks (the run reports a vote that ended short).

**The recovery family is built** (`account_recovery.py`, the CI `recovery-campaign` step after the governance family): both types, every recovery transaction made by the release CLI's recovery commands (prepare, sign with each key, assemble, sponsor, submit) and paid by a separate sponsor, as the recovering account never pays. The node verifies every signature and then checks a recovery at admission against the committed state exactly as the block would, so both types are refused there, uncharged, with the rule as the log. The targets first enroll three fresh guardian keys each, followed to the sponsor receipt, verified against the application hash. A replayed recovery is a target's committed enrollment again: either the committed transaction byte for byte (the CLI signs deterministically, so signing it again makes the same bytes), asked at admission directly (`check_tx`) since the engine's cache answers bytes it has seen before the node can, and checked to be the bytes the node hashed; or its operation sponsored again at the sponsor's current nonce (a new authorization for the same operation), sent. The node answers "Consumed sponsorship or successful operation". A replay must reach the node before the operation's submission expiry (the account template's 17,280 blocks), after which the node refuses it as expired and prunes its receipt, so the replays stop with an error when too few blocks are left. A wrong-key recovery is a recovery start signed in the guardian role by two outsiders, a guardian and an outsider, or a guardian and the account's own active key, prepared by the CLI from the target's view with those keys named as its guardians: the operation names only the policy version and recovery sequence, so only its signers are wrong, and the node answers "signer is not a current guardian". Each attempt counts only when the node gave the type's reason, its row's fault is the type's (for a replay the committed operation, its receipt a success, the attempt not expired; for a wrong key the signers against the policy and active key read from the chain) and the target's recovery state and the sponsor's nonce and liquid DRT are unchanged; admission or any change is a success. The positive controls: each target's enrollment, and after each type a fresh wallet's enrollment, each committed a success by its verified receipt with the policy then on the chain. CI runs each type 10 times against 2 targets; the staging hosts run 3,000.

## Scenario register

`launch-rehearsals.json` keeps the twenty mandatory scenarios (L01 to L20) that the runs cover and the brief's verbatim instructions. L01 and L02 are local prerequisites (`scripts/run_launch_rehearsals.py`); L18 is the seven runs; L19 the frozen candidate's operating periods; L20 the launch decision. Under the solo launch profile, "independent operators" and "independent reviewers" mean what the gate data's `acceptance_profile` says.

## Evidence

Each run records: the run ID, start and end, status and the founder's sign-off; the source revision, the release manifest and binary digests, the genesis and configuration digests, the rehearsal chain ID and the shortened timing set; the node identities (public only), the workload, the injected faults and their timing; per-node finalized heights, app hashes and supply reconciliations; client receipts, resource metrics, alerts and logs; expected and actual results and every assertion. The evidence files are hashed. Success is never inferred from a process exiting.

The launch page shows public summaries of the evidence, never the evidence itself: `results.py` reduces it to counts, times and pass or fail, signed with the results key ([approval](../../../launch/approvals/P01_T06_RESULTS_KEY_2026-11-02.json); public key in `launch/simulations/RESULTS_KEY.json`), and `launch_dashboard.py` takes each KPI from the newest signed summary that reports it. The first summarizer covers the fault recoveries: network heal and validator restart from the fault injector (T5), a sentry rebuild from the restore drill (R6) and a lost validator host from the validator recovery drill (T9), each against its approved target; the runs, checkpoints, attacks, performance and endurance follow.

A run stops on conflicting finality or an unexplained accounting difference: the evidence is preserved, the cause fixed, and the affected runs rerun. A change to consensus, economics, cryptography or persistence invalidates the affected results. A testnet-style database reset is never a mainnet recovery procedure.

## Local prerequisites

`scripts/run_launch_rehearsals.py` runs the local prerequisites only (L01, L02) and records the distributed scenarios as blocked; its report always sets `mainnet_ready` to false.

```sh
python3 scripts/run_launch_rehearsals.py --profile components --output /absolute/path/outside/repository/new-run
```

Use `--profile preflight` for the reference and module checks only, and a new output directory per run. Cargo runs locked and offline. The runner hashes tracked and non-ignored untracked files before and after; a source change invalidates the run.
