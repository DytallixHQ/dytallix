# Public runtime binding review

`check_bindings.py` checks supplied data. It never creates genesis, starts a node, signs a record, or enables production.

Run from the node repository:

```text
python3 -B tools/mainnet-preparation/check_bindings.py \
  --bindings BINDINGS.json --records PRODUCTION_INPUTS.json \
  --native NATIVE_GENESIS.json --application APPLICATION_CONFIG.json \
  --service SERVICE_CONFIG.json --engine ENGINE_GENESIS.json --manifest BUILD_MANIFEST.json
```

The native, application, service, engine genesis (`--engine`) and builder manifest (`--manifest`) files are optional. Without them, the result lists the missing runtime bytes. Exit code 1 means the review remains BLOCKED. Exit code 2 means a supplied field or source binding failed validation. No exit code grants acceptance.

The records argument uses the existing `PRODUCTION_INPUTS` record IDs and row arrays. Run the separate intake checker to validate the complete record schema and acceptance state. This tool checks only the records used by its supported bindings. A record reference does not establish approval.

## Supported typed inputs

| Input | Check |
|---|---|
| Exact source bytes | Match SHA-256 for the supplied records, native genesis, and application configuration. Match the application's embedded native-genesis digest. |
| Native amounts | Require decimal strings, u128 bounds, the existing DGT cap, unique accounts, explicit vesting, and checked stake funding. Match funded delegations to reward positions. Report `full_dgt_issuance` as missing unless genesis issues the whole 1,000,000,000 DGT: all DGT is issued at genesis and nothing mints it later (D05-Q02). |
| Native reward and issuance inputs | Check the current development versions, activation height, decimals, resource limits, validator population, controller bounds, and epoch budget. |
| Application configuration | Check the profile, chain ID, gas and byte limits, canonical ML-DSA-65 public key encoding, unique identities, positive bounded power, and reward-validator agreement. Report `recovery_and_ordinary_profiles` as missing unless both profiles are present: they are the only user-transaction paths (E04 gap 14). Report `lifecycle_and_penalty_profiles` as missing unless both are present: they penalize double-signing and allow withdrawals (penalties v1). |
| Full configuration (E05-d2) | `config_checks.review` re-derives, independently of the node: lifecycle, penalty, recovery, ordinary, governance and root-control structure; every account address from its origin key (SHA3-256 and Bech32m); the validator-proof profile digest; the E05-a rules (fee caps, transport bound, governance thresholds and bounds, root control bounds, evidence seconds); validator power as bonded stake and self-bonds at the minimum; recovery accounts equal to native accounts; root policies bound to the native genesis; upgrade keys disjoint from emergency keys; and the development gates the node still requires. |
| Engine genesis (E05-d2) | The engine genesis ends with the exact native genesis as `app_state`; chain, initial height, key profile, evidence limits equal to the lifecycle's, validator addresses and powers equal to the application's. Its digest binds through `source_digests.engine_genesis_sha256`. |
| Builder manifest (E05-d2) | Each file's size, SHA-256 and SHA-512, and the build digest. |
| Service configuration | Report `service_configuration` as missing unless supplied, and `metrics_output` unless it sets `metrics` (an absolute `directory` and `interval_seconds` from 1 to 3600): the incident runbooks read the metrics files (E04 gap 15). No other service field is reviewed. |
| Chain identity | Resolve the D13-Q02 identity policy reference to a typed public document. Match its chain ID to both runtime files. |
| Genesis time and governance | `genesis_time` equals the engine genesis's; `governance_parameters` equals the configuration's governance section exactly. |
| Beneficiary bindings | Resolve D08-Q01 account references. Match amounts, explicit vesting documents, staking permission, and operator-specific funded delegations. Require every native account and supplied allocation row to map exactly once. |
| DRT bootstrap | Match each D08-Q03 row to its recipient account and policy reference. Reconcile all rows and the policy total with native DRT balances. |
| Validator bindings | Resolve D09-Q02 operator references to exact public key documents. Match keys to the application validators. Reject duplicate operator or validator mappings. |
| Public transport manifest | Check the Go loopback profile, timeout and peer limits, full public key pins, SHA-256-derived 20-byte peer IDs, addresses, and persistent-peer agreement. |

`source_digests` identifies exact input bytes. `runtime_inputs` retains the eleven existing preparation field names. `public_documents` resolves public references with typed payloads and hashes. The fixture shows every supported field shape.

Public document entries contain `reference`, `sha256`, and `document`. Supported document kinds are `account`, `validator_key`, `peer_key`, `vesting_terms`, and `identity_policy`. Each kind rejects unknown fields. Private key fields are not accepted. Hash each document as sorted-key compact ASCII JSON with one final newline. This package convention is not a general JSON canonicalization standard.

No reference causes a file or network fetch. The tool reads only explicit command arguments. It limits each input to 8 MiB and JSON nesting to 64 levels. Duplicate keys and non-finite numbers fail.

## Consumer limits

These checks implement a strict supported subset of the current Rust and Go consumers. The native subset requires explicit `udgt` and `udrt` fields, vesting, delegations, reward state, and issuance inputs. It rejects omitted development defaults and alternate delegation representations. Canonical decimal strings are stricter than the native parser's digit-only strings.

This adapter permits one validator per operator record. It does not establish the production policy for operators that control several validators. The record format permits one initial operator delegation per beneficiary row. This version does not combine beneficiary rows or invent a multi-operator record. Allocation amounts must match native genesis credits exactly. D05-Q02 (P01, 29 September 2026) excludes a partial genesis mint, so the review requires the full total rather than inferring it from the one-billion-token allocation.

The application check enforces the consumer's 8 MiB limit (`MAX_CONFIG_BYTES`, E05-a) on the exact supplied file bytes; the configuration carries the genesis recovery accounts, about 15 KB each. The public transport check covers the typed manifest and peer tuples. Scoped IPv6 addresses are rejected because the Go loopback parser does not accept them. It does not inspect a full Go TOML configuration, its canonical transport file bytes, loaded private keys, private file permissions, or the complete engine genesis. It does not test a handshake or key possession.

## Unsupported fields remain open

SLH-DSA root authorization and approval-bundle semantics have no typed adapter in this tool. They remain UNSUPPORTED when populated. No populated string or object can make `runtime_complete` true.

The tool does not establish production activation, custody, signature authenticity, validator admission, stake-to-power policy, or independent review. The supported runtime profiles remain local development profiles. Mainnet remains NO GO.

## Emergency custodian intake

`emergency_custodian_intake.py` checks a completed emergency custodian packet, the first of the three custody intakes. The packet format and collection steps are in [the emergency intake](../../../launch/custody/emergency/INTAKE.md).

```text
python3 -B tools/mainnet-preparation/emergency_custodian_intake.py EMERGENCY_INTAKE.working.json
```

It requires five custodians (or solo kits), three of five for freeze and three of five for resume, one explicit authority epoch, and SLH-DSA-SHAKE-256s keys. It checks distinct controllers and control groups (one controller and five distinct kits under `solo_kits`), ten distinct keys with SHA-256 key IDs, purpose- and epoch-bound public evidence and reviewer separation. On success it emits `authority_fragment`, the `root.emergency` records shape: the epoch and the freeze and resume key sets, each sorted by key ID with threshold 3. The upgrade and genesis checkers read the same packet through `--emergency`. It does not verify signatures, identity or independence, and it never reports production acceptance. Exit code 0 means structurally complete; 2 means incomplete or invalid.

## Upgrade custodian intake

`upgrade_custodian_intake.py` checks a completed upgrade custodian packet (E05-c). The packet format and collection steps are in [the upgrade intake](../../../launch/custody/upgrade/INTAKE.md).

```text
python3 -B tools/mainnet-preparation/upgrade_custodian_intake.py \
  UPGRADE_INTAKE.working.json --emergency EMERGENCY_INTAKE.working.json
```

It requires exactly five custodians, three of five, one explicit authority epoch, and SLH-DSA-SHAKE-256s keys (P01, 30 September 2026). It checks distinct controllers, control groups and keys, SHA-256 key IDs, purpose- and epoch-bound public evidence, reviewer separation, and that no controller, control group or key also appears in the complete emergency intake. On success it emits `authority_fragment`, the node's upgrade authority shape with keys sorted by key ID. It does not verify signatures, identity or independence, and it never reports production acceptance. Exit code 0 means structurally complete; 2 means incomplete or invalid.

Both custody checkers take the packet's `custody_model`. `independent` applies the rules above. `solo_kits` is the solo launch profile (P01, 3 October 2026): one controller in all five slots, five distinct kits as the control groups, no independence review, and the same controller and kits in the emergency, upgrade and genesis packets. Keys stay distinct across every role in both models.

## Genesis signer intake

`genesis_signer_intake.py` checks a completed genesis signer packet. The packet format and collection steps are in [the genesis signer intake](../../../launch/custody/genesis/INTAKE.md).

```text
python3 -B tools/mainnet-preparation/genesis_signer_intake.py GENESIS_INTAKE.working.json \
  --emergency EMERGENCY_INTAKE.working.json --upgrade UPGRADE_INTAKE.working.json \
  --policy-out root-genesis-policy.json
```

**What it checks:**
- The approved shape (P01, 30 September 2026): exactly five signers, three of five, the chain ID, and SLH-DSA-SHAKE-256s keys as `dytallix-root-sign keygen` writes them (`key_id`, `public_key_hex`).
- Distinct controllers, control groups and keys, with SHA-256 key IDs.
- Public evidence bound to the purpose `genesis`, with no epoch.
- Reviewer separation.
- That no controller, control group or key appears in the complete emergency or upgrade intake.

`five_holder_custody.py` checks the three packets together under the five key holders model (`"custody_model": "five_holders"`; P01, 7 October 2026: five people, one kit each, kit N holding key N of every role). Each packet must pass its own checker, and together:
- slot N is named only by its kit, `kit-holder-N` in `kit-N`, in every packet, so the five holders are the same in every role;
- the twenty keys are distinct across roles, and the emergency and upgrade keys share one authority epoch;
- no slot carries an independence review: the public disclosure stands in for it (P01, 10 October 2026, D10-Q03).

```text
python3 -B tools/mainnet-preparation/five_holder_custody.py --emergency EMERGENCY_INTAKE.working.json \
  --upgrade UPGRADE_INTAKE.working.json --genesis GENESIS_INTAKE.working.json --policy-out root-genesis-policy.json
```

It outputs the two authority fragments, the genesis signer policy and each packet's SHA-256. Like the other checkers it verifies no signature, identity or independence, and accepts nothing.

**On success:** it emits `signer_policy`, the public signer policy record. It is byte for byte what `dytallix-root-sign policy` writes from the same records, which `fixtures/genesis-signer-policy` and the signer's own test check. `--policy-out` writes it to a new file.

**What it doesn't do:** verify signatures, identity or independence. It never reports production acceptance.

Exit code 0 means structurally complete; 2 means incomplete or invalid.

## Host files (E05, host setup v1)

`host_files.py` writes each host's files ([host setup v1](../../docs/architecture/host-setup-v1.md)) from the release (`RELEASE_MANIFEST.json`, `BUILD_RECORD.json`), the chain's genesis and root records, `dytallix-host-config`'s output, the pin plan, the offline key summaries (`LABEL.keys.json`, schema `dytallix.host-keys.v1`: the host's public keys and the SHA-256 of each sealed secret file; each serving host's `LABEL.channel-pin.json`), the approved E05 values and `launch/hosts/SETUP_VALUES.json`:

```text
python3 -B tools/mainnet-preparation/host_files.py --release RELEASE_DIR --chain CHAIN_DIR \
  --hosts HOSTS_DIR --plan PIN_PLAN.json --keys KEYS_DIR --out OUT_DIR
```

For each host, `OUT_DIR/LABEL/` holds every file under its installed path and `INSTALL_MANIFEST.json` (schema `dytallix.host-install.v1`): owners, modes, digests, directories, binaries and the secret files the sealed keys must provide. It runs `native-execution-policy/production_roles.py` for the role profiles, unit properties, admission and firewall table, and pins every file the supervisor reads by SHA-256. The plan's home must be `/var/lib/dytallix/node`. `fixtures/host-files-staging/` holds the configurations it writes for a synthetic staging network (the two seats, the sentry serving clients, plus an endpoint), which the supervisor's tests parse with their own types.

`host_keys.py` is the offline key step, run on the ceremony machine with the release's key tools ([key ceremony, node keys](../../../launch/custody/KEY_CEREMONY.md#node-keys)). For each host in the pin plan it makes the peer seed, the validator key and signing state and, on each host serving clients, the client channel seed and pin in a staging home; writes `LABEL.keys.json`; seals the secret files with `dytallix-root-sign seal`; and has the founder type the printed seal code back (`seal-check`). With `--backup-upload FILE` the sentry also seals the chain's backup code and the store's upload key; with `--history-upload FILE` the chain's history code is made once and sealed, with that separate upload key, on every host (monitoring v1, M4b). Its output directory holds only public files, with the pin plan's public keys filled in:

```text
python3 host_keys.py --plan PIN_PLAN.json --bin BIN_DIR --staging /tmp/staging --out KEYS_DIR
```

`host_bundle.py` packs one host's bundle from `host_files.py`'s output, the release's `bin/` and the host's sealed keys, checking every file against the install manifest with the installer's own check, and writes `LABEL.bundle.tar` (deterministic) and its `.sha256`. `host/` holds what the bundle runs on the host: `install.sh`, `stage.sh`, `switch.sh`, `restore.sh`, `monitor-settings.sh` and `wipe.sh`, wrappers for `host_install.py install|verify|stage|switch|restore|monitor-settings|wipe` (standard library only); `restore.sh COPY` restores a freshly installed host from an off-host copy (disaster recovery v1, R5), and `monitor-settings.sh FILE` installs or replaces the host's webhook URLs (monitoring v1, M4). The host files also carry the jobs the timers run: the sentry's `backup.py` and every host's `monitor.py`, which reads the node's metric files and the host's counters each minute, evaluates the approved alert rules (E05 values `monitor.*`) and pushes a heartbeat and alerts with curl ([monitoring](../../docs/operations/monitoring.md)); With the history secrets it also encrypts and uploads each finished day of its history. `test_monitor_job.py` runs it with stand-in systemctl, curl and signer. `test_host_bundle.py` runs the key step with stand-in key tools, builds bundles and installs, verifies and wipes them against a temporary root with a stand-in system; H4 installs on a real Ubuntu 24.04 runner.

`staging_chain.py` builds a throwaway production-profile staging chain and every host's bundle from a filled pin plan, the key step's output and a release build, with the release's own `dytallix-genesis-build`, `dytallix-host-config` and `dytallix-root-sign`: the approved allocation's shape on spendable rehearsal accounts (the five buckets, the treasury, the five holders' grants and each validator's operator with its self-bond, their ML-DSA-65 keys made by the release's CLI in `rehearsal-wallets/`, with `MAPPING.json` naming the production row each stands for) with the plan's validators, the genesis built twice around the release manifest (the native genesis must not change), five throwaway root keys signing three of five, the host values and configuration, host files and bundles. It refuses the approved network identity and any chain ID naming mainnet or production. `staging_host.py prepare` writes a staging plan with this host as the validator and runs the key step and `staging_chain.py`; as root, `install` installs the validator's bundle, starts the node and waits for its height, and `wipe` removes it. The Host install workflow runs them on an Ubuntu 24.04 runner.

`staging_network.py` runs the two seats on one runner (the validator, and the sentry serving clients; P01, 11 October 2026): `prepare` (the plan on a private bridge, the key step with a stand-in upload key for the sentry's backups, a staging snapshot interval of 10 blocks), and as root `network-up` (bridge, taps and a temporary route out), `vms-up` (the sentry's KVM virtual machine from the Ubuntu 24.04 cloud image, with cloud-init giving it its address, the guest agent and its bundle), `install-vms`, then `staging_host.py install` for the validator, then `run` (the sentry follows the validator; its status page; one run of each host's monitor job in its sandbox; the sentry's snapshot and backup, opened on the runner), `wallet-drill` (the rehearsal wallets over the sentry's client channel with the release's CLI: a DRT transfer creating an account, a DGT transfer, a bond to the validator and a reward claim, each by its committed receipt and proven balances, with the supply rule before and after, and the ledger of its writes; simulation plan, T1), `reconcile` (the reconciliation report, below), `load` (the load generator, below) and `reconcile --after load` (the reconciliation over the load's ledger), `restore-drill` (the first restore drill, disaster recovery R6: the sentry wiped, reinstalled and restored from its copy with `restore.sh`, then matched against the validator's height and hashes, with the measured times; digest-bound evidence by `restore_drill.py`, which `restore_drill.py verify --evidence FILE --genesis NATIVE_GENESIS` re-evaluates against the approved 4-hour sentry objective), `kit-drill` (root kit replacement K4), `monitor-drill` (monitoring v1, M5: the sentry's monitor reports to a stand-in alerting service, and a restart loop, a full disk, a halt and a stopped monitor each alert and resolve under the approved rules), `stage-later-release` (simulation plan, T8: the second release, built with `prepare --later-release` by `staging_chain.later_release` with the genesis release kept for the root, staged beside the running one on both hosts with `stage.sh`), `upgrade-drill` (simulation plan, T8: the handover to that release with the receipt-index migration, its controls signed three of five, RC1 stopping itself at the activation and `switch.sh` on both hosts; evidence by `upgrade_drill.py`, which `upgrade_drill.py verify --evidence FILE --genesis NATIVE_GENESIS` re-evaluates), `alerts-up` and `fault-alerts` (T5 fault alerts, P01 9 November 2026: a stand-in alerting service on the runner with both hosts' monitors reporting to it, the sentry's through a relay on its loopback; after host loss, digest-bound evidence by `fault_alerts.py` of what fired and resolved within the partition's, host loss's, the sentry rebuild's and the validator host's windows, each fault's decided alerts firing before its recovery and resolving after it, or at most one monitor period (60 s) before it; in CI the sentry rebuild and the validator host are held down as long as host loss so their alerts must fire (P01, 10 November 2026); `fault_alerts.py verify --evidence FILE --genesis NATIVE_GENESIS` re-evaluates it), `agent-drill` (simulation plan, T2: the staging agent on the sentry runs signed commands and refuses tampered, unsigned, replayed, non-allowlisted and expired ones; its encrypted results open on the runner; `wipe.sh` removes it) and `diagnostics`. `s3_standin.py` is the stand-in store: loopback only, signed PUTs and, for the command store, signed GETs from its read key; never a real store. `alert_standin.py` is the stand-in alerting service: on the loopback (and, for the fault alerts, the runner's bridge address), it records heartbeats, alerts and escalations and alerts on a heartbeat missing for 3 minutes, never a real service; with `--relay URL` it only forwards each POST to another stand-in.

`reconcile.py` is the reconciliation report (simulation plan, T6). It reads each node through a host transport (anything with `run` and `read`: `LocalHost`, the staging network's guest agent); a console-only host is read through the staging agent instead (`collect_through_agent`: its read-only `reconcile-read`, sent to every host for one minute, and the readings its sealed result carries, with no state check): the engine's newest block hash and header application hash from the operator socket, and the application's supply buckets at their height from its metrics file; and the public node through the release's CLI: status views and the tracked accounts' proven balances. It then compares one block hash and one application hash per height on every node (a header at H carries the hash after H − 1), up to the newest height every node's engine was read at; requires each node's supply at a height every node's application hash attests (the application writes its metrics every metrics interval, 15 s, on each node's own phase, so two nodes' supply readings need not share a height), and compares the buckets wherever they do; applies the supply rules to every reading (the supply mismatch runbook's, the DRT genesis and DGT issued against the native genesis, no fee left withheld); checks emitted and burned only grow; sums the tracked accounts against the liquid totals inside a window in which neither moved; checks the burns since an earlier reading against a ledger of the committed transactions (`dytallix.reconcile-ledger.v1`: each charge plus the creation fee per created account, fees v1); and runs `dytallix-state-check` on a copy of one node's database, taken while that node is stopped, against the hash the other nodes' headers record. Any difference is FAIL; a reading that could not be made is INCONCLUSIVE; only PASS exits 0. The evidence (`dytallix.reconciliation.v1`) keeps every reading and its SHA-256; `reconcile.py verify --evidence FILE --genesis NATIVE_GENESIS` checks the digest and re-evaluates it. `staging_network.py reconcile` runs it after the wallet drill, with the drill's ledger.

`load.py` is the load generator and wallet fleet (simulation plan, T3). `fleet` makes the wallets with the release's CLI (`wallet create`, `wallet export`) into owner-only key files: the load wallets, a governance proposer, depositor and voters, and spare keys whose accounts the run creates; `fleet.json` holds only labels, roles, addresses and account IDs. `run` starts `dytallix gateway serve` on a loopback port and drives JSON-RPC through it over the release's client channel; funds the fleet from a rehearsal account (sixteen transfers a transaction; with `fleet --distributors` it fans out, the funder paying the distributors and the primed distributors paying their shares in parallel, P01, 12 October 2026); primes each wallet with its first spend through the CLI's online path (funding and priming are the warm-up, timed in the record and outside the load metrics); then paces `--rate` transactions a second for `--duration` in the `--mix` (`send_drt`, `send_dgt`, `create`, `bond`, `unbond`, `claim`), each signed offline (`ordinary prepare`, `sign --key-file`, `transport`) at the wallet's locally tracked nonce, one in flight per wallet, broadcast in batches of up to 10 with the head height in the same request, and followed to its receipt. `--connections` bounds the channel requests in flight, the CLI's included (2 per address). With `--governance` it proposes a no-op parameter change and deposits the minimum, and with `--governance-vote` votes once the deposit period closes; v3 has no receipts, so each charge is the fall in the wallet's liquid DRT around its spent nonce. With `--sweep-from NAME` each named keystore account (the operators, the stakers) claims its rewards every `--sweep-interval` seconds (about hourly) and sends its liquid DRT above `--sweep-keep` back to the funder, so the genesis allocation stays the production one. It writes `transactions.jsonl`, `ledger.json` (`dytallix.reconcile-ledger.v1`, from its first status view), `accounts.json` (the accounts it created) and `evidence.json` (`dytallix.load-run.v1`: inclusion delays, throughput per block, block intervals, response times, refusals, lost transactions, supply and burns, with the SHA-256 of each file); PASS needs nothing lost, 99% within 2 blocks, the liveness thresholds, the supply rule and burns equal to the ledger. `load.py verify --evidence FILE` recomputes it from the files. `staging_network.py load` runs a CI-sized run: 16 wallets funded through 2 distributors, 1 transaction a second for 2 minutes, with governance propose and deposit and one reward sweep from `operator-1` and `kit-holder-1`.

## Staging agent (T2)

`recovery.py` is the validator recovery drill's evidence (simulation plan, T9; [validator recovery](../../docs/operations/validator-recovery.md), F17). `staging_network.py validator-recovery-drill` fences the runner's validator (its `wipe.sh` stands for the provider deleting the server), confirms the halt at H on the sentry, sets the sentry's old votes aside, installs the replacement from its bundle and starts the sentry and then the validator, which block-syncs to H and signs from H + 1. The record checks the procedure's order, the halt, both nodes past H with one state, the validator set unchanged and the host verifying, and the time against the approved 8-hour objective; `recovery.py verify --evidence FILE --genesis NATIVE_GENESIS` checks its digest and re-evaluates it, refusing any target other than the objective.

`staging-agent/agent.py` and its `ALLOWLIST.json` are the staging agent ([staging agent v1](../../docs/architecture/staging-agent-v1.md)): staging only, never in a release or a host bundle. On a console-only host, after the node's install, `agent.py install --settings FILE` adds it with a timer on every minute; each poll on the minutes its settings' `poll_every_minutes` names (2 on the staging hosts, to stay inside the store's free tier: P01_T06_AGENT_POLL_FREE_TIER_2026-11-04) fetches the next command by sequence from the command store, runs it only if its ML-DSA-65 signature verifies (the release's `dytallix crypto verify`, the key pinned in the settings) and it is bound to this host, this chain and that sequence, unexpired and on the allowlist, and uploads every result, refusals included, encrypted under the history code. `wipe.sh` removes it and `install.sh` refuses a host that has it. `staging_command.py` is the founder's side: `key` (the staging command key, made with `dytallix wallet create`), `settings`, `make` (allowlist check, `dytallix crypto sign`, self-check) and `package` (the agent's archive and its SHA-256). `staging_founder.py` drives a console-only host from the founder's machine through public paths only (the store's S3 API with the founder's key, the sentry's status page, the client channel): `send` signs and uploads a command at the next free sequence and opens its result (a wait lists the results only after the agent's looks, and the store record's optional `daily_budget` caps the founder's listings and downloads a UTC day across every tool), `open` lists and opens every result with the history code, `reconcile` runs the reconciliation through every host's agent (exit 0 only on PASS), `status-page` reads the page, `preflight` reads only and lists the founder's store checks. `faults.py run` drives the fault scenarios on a real host through it; the CI `agent-drill` (which ends with the reconciliation through the agent) and `fault-drill` use the same calls.

## Launch page data (T7)

`launch_dashboard.py` builds `launch/simulations/dashboard.json`, the data of the launch page (dytallix.com/developers/launch, schema `dytallix.launch-dashboard.v1`), from `launch/simulations/DASHBOARD_DEFINITIONS.json`. Each KPI's status and value come from the record the definitions name: an approval record's date; a tool's build date, which must match its CI step named "(Tn)" in the host install workflow; or results, which stay planned until the collector publishes signed result summaries (`launch/simulations/results/`). Phases roll up from their KPIs as the page does. It applies the page's own checks (no addresses, the page's ID, unit, status and size rules) plus no launch server names and evidence links that resolve in this repository. Run it with no arguments to check that the committed file is current (it ignores only `project.commits_at_as_of`); regenerate it from a full clone, after any change to its inputs or a new approval record:

```text
python3 -B tools/mainnet-preparation/launch_dashboard.py --write
```

## Result summaries (results pipeline)

`attacks.py` is the attack campaign's transaction family (statistical campaign: at least 3,000 attempts per attack type with zero successes). `run` funds and primes a fleet as `load.py run` does, then makes N attempts of each type, each with its own bytes: mutations of one valid transaction never sent (a flipped signature byte, a truncated signature, an undecodable or trailing-byte envelope, an oversized request); transactions the release CLI signs against a falsified view (another chain ID, the account's mainnet identity, another wallet's key as the current key); expired ones held past an expiry two blocks ahead; a stale nonce and an overspend; and a valid original with its duplicate, re-signed copy, conflicting and future nonce in one request. An attempt counts only when refused for its type's reason; an admitted one is a success; a refusal for another reason fails the type. `attacks.json` and `attacks.jsonl` hold the record and its rows (no address); `verify` recomputes everything from the rows. The CLI will not sign fee_cap_below_minimum or too_many_actions, so with `--attack-client` the attack client (`node/tools/attack-client`, campaign and CI only) re-signs a transaction the CLI made after that one change; without it those two types are not run. `test_attacks.py` runs whole campaigns against a stand-in node that applies the admission rules to the campaign's own bytes.

`root_controls.py` is the attack campaign's root-control family. `staging_network.py root-control-campaign` runs it after the kit drill: the release tools and the staging kits make the genuine controls (a fresh freeze, the same freeze with a 24-block window, a signature by the freeze key the kit drill replaced, a fresh kit replacement) and the kit drill's committed freeze and resume are replayed. Each type's attempts are too few signatures, a replaced key, non-canonical bytes, an expired window, a replayed sequence and a kit replacement while frozen; the first is the genuine control with its one fault, later ones change one more field so each has its own bytes. An attempt counts only when refused for its type's reason with exactly its type's fields changed. `root-controls.json` and `root-controls.jsonl` hold the record and its rows; `verify` recomputes everything from the rows. `test_root_controls.py` runs whole campaigns against a stand-in node that checks a control in the node's order.

`results.py` is the results collector ([simulation inputs approval](../../../launch/approvals/P01_T06_SIMULATION_INPUTS_2026-10-14.json); results key, [approval](../../../launch/approvals/P01_T06_RESULTS_KEY_2026-11-02.json)). `summarize campaign --faults FILE ...` reduces the fault injector's records (T5), each re-verified against the genesis files and required to carry the approved target, to a cumulative campaign summary (`dytallix.launch-result.v1`, `launch/simulations/results/campaign/DATE.json`): `campaign.faults.network_heal` (the partition, 120 s) and `campaign.faults.validator_restart` (300 s), each with its slowest recovery, samples and the 30 repetitions per quick fault; one miss fails it. `--restores FILE ...` and `--recoveries FILE ...` add the heavy faults from the drills' own records, each re-verified against the genesis and the approved objective (`launch/operations/OBJECTIVES.json`): `campaign.faults.sentry_rebuild` from the restore drill (R6, declared to caught up, 4 hours) and `campaign.faults.validator_host` from the validator recovery drill (T9, declared to the first block after the halt, 8 hours), with 3 repetitions each (the plan's 3 to 5 per heavy fault); an unfinished drill is no sample. `--alerts FILE ...` adds `campaign.faults.alerts` from the fault alerts records (`fault_alerts.py`): the share of conclusive in-scope faults that raised their alert and resolved it; one miss fails it, and it passes once each fault has the fault campaign's repetitions for it (30 for the partition and host loss, 3 for each heavy fault). Only real staging-host runs are published; CI's count toward the tools phase only. A summary holds numbers, statuses, the candidate (commit and release set) and its sources' digests, never addresses; it must pass `launch_dashboard.summary_problems` before it is written. `sign --cli DYTALLIX --home DIR SUMMARY` signs it with the results key (the release CLI, `dytallix crypto sign` over `dytallix-launch-results-v1:` and the summary's SHA-256) into `SUMMARY.sig`; `verify --cli DYTALLIX SUMMARY` checks it against `launch/simulations/RESULTS_KEY.json`. Run `verify` before each results pull request, then `launch_dashboard.py --write`. The CI fault drill runs the whole chain with a throwaway key; `test_results.py` covers it with a stand-in CLI.

## Load machines (Hetzner)

`load_machines.py` rents the load machines the simulation plan approves (P01_T06_LOAD_MACHINES_HETZNER_2026-11-03: four to eight of Hetzner Cloud's smallest x86 servers in the hosts' own project, by the hour, for R03, R06 and the campaign's flood runs, deleted after each use). `check` lists anything left running and any other server without delete protection; `up --count N --hours H --out DIR` makes a throwaway SSH key, creates the machines in nbg1, fsn1 and sin in turn (each labelled `dytallix-load=RUN`), waits until each is running with a public address, writes `DIR/machines.json` and starts a detached watchdog that deletes them at the deadline; `down --out DIR` deletes them now (the watchdog then stops), and `reap` deletes every labelled machine and every key the tool registered. At most 8 machines, the smallest types (cpx02, cx23, cpx12), 12 hours, never hel1; `up` refuses while any labelled machine exists or any other server lacks delete protection, and deletes everything it made if it fails. The tool deletes only servers that carry its label, its name prefix and no protection. It runs the hcloud CLI with `--context` (default `dytallix`) on every call and strips `HCLOUD_*` from its environment, so the token stays in hcloud's own configuration; `test_load_machines.py` runs the tool against a stand-in `hcloud` that keeps a project in a file.


`load_workers.py` drives the load from them (simulation plan, T3): `drive --workers N --machines RUN_DIR --worker-cli DYTALLIX` (or `--local`, with `--namespaces` and `--addresses` for one address per worker) funds the fleet from the funder here, splits the load wallets and spare keys into disjoint shares, ships each machine its share, the release CLI, `load.py`, `load_workers.py`, `config_checks.py`, `native_checks.py`, the application config and a CLI home holding only `chain.json`, and starts `work` there over SSH with the run's throwaway key (host keys pinned in the run folder). Each worker primes its wallets and reports; once all have, drive sends one start time, and each runs the window at the total rate over N. drive collects every worker's rows and writes one `evidence.json` and `transactions.jsonl` for `load.py verify`, with each worker's address, rows digest, start lateness and signing and read times. N times `--connections` must fit the channel's 16, at most 2 each; a worker that fails stops the others and fails the run (`failure.json`). `test_load_workers.py` runs it over test_load's simulated chain with a thread per worker, and the transports against a stand-in ssh and local processes; the CI staging network runs it with three workers in network namespaces (`staging_network.py load-workers`).

`flood_workers.py` runs the flood family (T4) from them for the real-host run against the production queue bound (R03; built, not run: renting and the run each need their approval): `drive --workers N --machines RUN_DIR --worker-cli DYTALLIX --genesis ... --engine-genesis ...` funds the fleet here, splits the queue bound plus 16 flood wallets into disjoint shares (load_workers.py's shares, files and transports, with `flood_workers.py`, `floods.py` and their imports added), and each machine primes its share. A transaction flood: every machine signs its share, drive reads the head once and names a target head (`--lead` seconds ahead), and every machine sends its whole share as its own head reaches it; drive merges the rows and judges them as one flood with floods.py's rules. A request flood: every machine stops its own gateway, 7 of them run `floods.py hammer` (2 connections each, 14 of 16) from one start time, and drive is the honest client on the founder's address. Fewer than 7 machines refuse the request flood. The record is floods.py's, so `floods.py verify` checks it; each machine's address is only in `workers.json`. `test_flood_workers.py` runs it with a thread per machine over a stand-in sentry.
## Decision copies (E05)

Each gate in `launch/LAUNCH_GATES.json` lists its decision dependencies as copies of questions in `launch/MAINNET_DECISION_REGISTER.json` (`source_ref`), and its `decision_counts` copies the register's `question_counts`. The register is authoritative. After recording an approval there, run:

```text
python3 -B tools/mainnet-preparation/decision_copies.py --write
```

It copies each question's kind, status, text, blocking output, assignee, reviewer and approval record into every copy, and the counts. It never changes a gate's status or the register. Without `--write` it reports each difference and exits 1; `test_decision_copies.py` fails the same way, so a register change without its copies fails CI.
