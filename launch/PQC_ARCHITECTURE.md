# Dytallix PQC architecture

Status: the production profile is approved and built; its qualification on the frozen candidate is open. Mainnet remains **NO GO**. Current as of 10 October 2026; the September version is in this file's history.

The production profile (D06-Q01, P01, 25 September 2026): ML-KEM-768 and ML-DSA-65 for authenticated pinned peers, ML-DSA-65 for validator signatures, distinct keys by role, exact approved IP endpoints, and no classical or plaintext fallback. Root keys use SLH-DSA-SHAKE-256s ([custody approval](approvals/P01_E05_CUSTODY_2026-09-30.json)). P01 decided on 28 September 2026 that no classical public-key cryptography is used anywhere in the stack, client edges included.

| Role | Algorithm | Implementation |

SecretConnection, its X25519 exchange and ChaCha20-Poly1305 were deleted from the fork ([PQC build boundary](../node/consensus/cometbft/PQC_BUILD_BOUNDARY.md), [client channel v1](../node/docs/architecture/client-channel-v1.md)). | Validators, votes and proposals | FIPS 204 ML-DSA-65 | A validator signs with its local key; the remote signer was removed. Registration needs a possession proof. Sentries and endpoints run a signer that refuses every signature. |

ML-KEM establishes a shared secret. It does not authenticate a peer. Peer authentication binds both identities, the chain, protocol version, roles and ephemeral key material to one transcript, and direction-specific keys with explicit key confirmation reject mismatched sessions. The transport also needs framing, bounded allocation, timeouts, replay handling, disconnect handling and secret erasure. Wire version 2 implements these; Hashlock audits it in the frozen candidate, and the launch is labeled unaudited until the report is published ([trust model](TRUST_MODEL.md)).

The production trust boundary includes consensus, P2P, account and wallet authorization, recovery, governance, trusted RPC and proof paths, root authorization, custody and the management channels that control these systems. An external service cannot escape this boundary merely because it uses TLS, SSH or a browser; its actual role is classified and its isolation verified.

No release binary contains classical public-key cryptography or TLS: the engine fork's classical code was deleted from source (E04 gap 20), and CI refuses a classical or TLS crate in any mainnet Rust lockfile (G35). Outside the release, each host's own `curl` carries the monitor job's webhooks and the encrypted backup and metric history uploads over TLS as transport only: every upload is already encrypted and authenticated, and nothing the chain trusts depends on that TLS ([monitoring v1](../node/docs/architecture/monitoring-v1.md), [disaster recovery v1](../node/docs/architecture/disaster-recovery-v1.md)). GitHub tags, checksums and signatures are classical conveniences that authorize nothing ([release](../release/README.md)). A dependency name does not prove runtime use, and an absent symbol does not prove isolation.

Operational keys never acquire root authority. A root signature binds a separately configured key, the chain, the action, a sequence, a bounded window and the artifact's SHA-512, so it cannot be replayed. ML-DSA-87 and the legacy Dilithium paths were removed from the verifier, and mainnet starts from one fresh genesis, so no legacy key state migrates.

AES-256-GCM, HKDF-SHA-256 and the hashes above are not prohibited merely because they are symmetric or hashing primitives; each use still needs review. A category-3 KEM does not establish category-3 security for a complete system. Truncated hashes and hash collision requirements need separate analysis. Consensus hash behavior is preserved until a reviewed migration exists.

The official standards are [FIPS 203](https://csrc.nist.gov/pubs/fips/203/final), [FIPS 204](https://csrc.nist.gov/pubs/fips/204/final) and [FIPS 205](https://csrc.nist.gov/pubs/fips/205/final). Check applicable errata during backend qualification. Algorithm use is not FIPS 140 module validation. No current result proves side-channel resistance or production custody.

Closure needs known-answer and cross-implementation tests, all-path integration and exact source and artifact hashes bound to the frozen candidate, the custody drills, Hashlock's audit of the frozen candidate, and the 30-day public review with a separate AI review labeled as AI ([audit](approvals/P01_E06_AUDIT_2026-10-10.json)). The seven simulation runs and the other launch gates remain open.
